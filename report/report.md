## 1. Введение и постановка задачи

Цель проекта: оценивать стоимость ремонта по фото комнаты/зоны (через извлечённые признаки) и опционально по тексту описания

Формулировка: задача регрессии (предсказываем число в рублях), после этого переводим в классы
- `< 90 000` - без ремонта
- `90 000 - 170 000` - косметический
- `>= 170 000` - капитальный

Метрики качества
- основная: `MAE`, потому что её легко читать в рублях (средняя ошибка прогноза)
- дополнительные: `RMSE` (штрафует сильные промахи), `R2` (доля объяснённой вариации), `MAPE` (ошибка в процентах)

## 2. Поиск и описание данных

Источник: свой датасет фото в `data/photo` (папки по типу помещения), признаки извлекались скриптом `src/make_csv_metrics_from_protos.py` в `data/room_dataset.csv`

Что в датасете
- 5859 строк, 17 столбцов
- 6 основных локаций: `bedroom`, `kitchen`, `frontyard`, `livingRoom`, `bathroom`, `backyard`
- признаки - табличные характеристики изображения: яркость, контраст, blur, количество объектов, дефекты, окна, плотность мебели и тд

Важно, реальной колонки с ценой в датасете нет, поэтому в `src/repair_cost_model.py` генерируется proxy-таргет `<synthetic_repair_cost>`

## 3. Обработка и подготовка данных

Что делали
- проверили пропуски и дубликаты: пропусков нет, дубликатов нет
- числовые признаки приводятся к `float`, категориальные к строкам
- при инференсе/обучении есть fallback
  - числовые пропуски - медиана,
  - категориальные - `unknown`

Feature engineering
- признаки получены из CV-пайплайна (`brightness`, `defect_score`, `furniture_density`, `num_windows` и др.)
- если текста нет, генерируется синтетическое описание `<synthetic_description>`

Сплит
- основной split: `train/test = 80/20`, `random_state=42`
- внутри обучения финальной модели есть `train/valid` для подбора веса текстовой ветки

## 4. Baseline-модель

Baseline: `DummyRegressor(strategy="median")`

Результат на test
- `MAE = 34 497.78`
- `RMSE = 42 061.00`
- `R2 = -0.011`
- `MAPE = 27.92%`

Это точка отсчёта, чтобы понять, есть ли польза от ML-моделей

## 5. Эксперименты

### Эксперимент 1
Гипотеза: линейная модель уже даст сильный прирост над baseline
Как проверяли: `Ridge` на числовых + категориальных признаках
Результат: гипотеза подтвердилась, ошибка сильно снизилась

### Эксперимент 2
Гипотеза: деревья лучше поймают нелинейности и взаимодействия признаков
Как проверяли: `RandomForestRegressor`
Результат: лучше линейной модели

### Эксперимент 3
Гипотеза: градиентный бустинг даст лучший баланс точности
Как проверяли: `HistGradientBoostingRegressor` + ordinal-кодирование категорий
Результат: лучший `MAE/RMSE`

### Эксперимент 4
Гипотеза: добавление текстовой ветки улучшит качество
Как проверяли: финальный `RepairCostEnsembleModel` (табличная + TF-IDF ветка)
Результат: вес текста `text_weight = 0.0`, т.е. на текущем датасете текстовая ветка не дала прироста

| Модель | MAE | RMSE | R2 | MAPE, % |
|--------|-----:|-----:|----:|--------:|
| Baseline (Dummy median) | 34497.78 | 42061.00 | -0.011 | 27.92 |
| Ridge (num+cat) | 10267.36 | 13163.59 | 0.901 | 8.26 |
| Random Forest | 9064.83 | 11343.62 | 0.926 | 7.52 |
| HistGradientBoosting | 8254.50 | 10202.05 | 0.941 | 6.87 |
| Финальная ensemble-модель | 8254.50 | 10202.05 | 0.941 | 6.87 |

## 6. Финальная модель и интерпретируемость

Финальная модель `RepairCostEnsembleModel` (основная табличная ветка `HistGradientBoostingRegressor`, плюс опциональная текстовая ветка)

Почему она: лучшее качество на test (`MAE = 8254.50`), улучшение к baseline ~`76%` по MAE

Интерпретация (permutation importance, MAE-based)
1. `furniture_density`
2. `location`
3. `num_objects`
4. `num_windows`
5. `defect_score`

Практический смысл: на цену сильнее всего влияют загруженность пространства, тип зоны и признаки изношенности

## 7. Деплой

Сделан сервис из 2 частей:
- FastAPI backend (`src/api.py`)
- Streamlit UI (`src/streamlit_app.py`)

Основные API-эндпоинты:
- `GET /health`
- `GET /model/info`
- `POST /predict/features`
- `POST /predict/csv`
- `POST /reload-model`

Запуск:
- локально: `uvicorn src.api:app --host 0.0.0.0 --port 8000` и `streamlit run src/streamlit_app.py --server.port 8501`
- через Docker: `docker compose up --build`

## 8. Заключение и выводы

Что получили
- рабочий ML-пайплайн от извлечения признаков до API/UI
- заметный рост качества относительно baseline (MAE 34.5k -> 8.25k)

Ограничения
- целевая переменная синтетическая, а не реальные чеки/сметы
- текстовая ветка пока не дала прирост

Что можно улучшить
- собрать реальные таргеты по стоимости ремонта
- добавить ручную валидацию признаков по комнатам
- дообучить/заменить CV-часть и проверить более сильные бустинги
